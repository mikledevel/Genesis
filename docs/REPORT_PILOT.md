# Разовый прогнозный отчёт с разбором

Обновлено 23 ноября 2026. Предмет первого пилота выбран владельцем: один отчёт с разбором, цена согласуется с клиентом. Это не покупка Pro на 30 дней. Автоматический checkout для такого SKU в этом выпуске не добавляется.

## Для участника

1. Подготовьте CSV или XLSX: дата и одна агрегированная метрика продаж. Удалите имена, email и платёжные реквизиты покупателей. При десятичной запятой предпочтителен XLSX. Для первого примера достаточно одной метрики с регулярной историей; пригодность покажет проверка.
2. Откройте **Forecast report**. До загрузки можно выбрать русский или английский язык. После загрузки укажите дату, метрику и горизонт в периодах данных, затем нажмите **Проверить данные**. Проверка не запускает обучение и не списывает оплату.
3. Подтвердите запуск, если он доступен для вашего согласованного пилотного доступа. Готовый результат содержит прогноз, сравнение с простыми методами, наблюдаемое покрытие и ограничения. Скачайте HTML RU/EN или CSV. Окно можно закрыть: результат открывается через **Мои отчёты**.

HTML работает без аккаунта и интернета после скачивания. Для PDF используйте печать браузера. Если надёжность низкая или диапазон не откалиброван, это существенная часть результата. Прогноз по одному ряду не является готовым планом закупок и не учитывает неизвестные акции, цены или отсутствие товара.

Если серверный запуск не включён, интерфейс сообщает это до расходования задания. Организатор согласует разовую услугу отдельно. Переход на платную подписку автоматически не выполняется.

## Организатору

- Уточнить метрику, единицы, горизонт, текущий метод клиента и конкретное решение, которому поможет отчёт.
- До реальных данных согласовать канал передачи, доступ и срок удаления. Сначала можно пройти путь на синтетическом примере.
- Использовать отдельный обычный аккаунт участника. Не передавать аккаунт владельца, администраторские данные и существующие credentials из `artifacts/`.
- Закрытый staging по-прежнему использует преднастроенные аккаунты. Полная регистрация с настоящим письмом не засчитывается без прохождения самим участником. Учётную запись, цену и действующий способ оплаты нужно согласовать до выдачи коммерческого доступа.
- Согласие на цену, pending invoice, фактическое поступление средств и выдачу результата фиксировать отдельно. Инвойс Pro не заменяет оплату отдельного отчёта.
- Попросить участника своими словами объяснить вывод и ограничение, измерить затраченное время и спросить, повторит ли он процесс на новой выгрузке. Это не заменяется автоматическим smoke-тестом.

## Реализованные контракты

- `POST /api/forecasts/preview`: принадлежащий пользователю `dataset_id`, разные `date_column` и `target_column`, целый `horizon` 1–365, `agg` sum/mean. Возвращает частоту, длину, пропуски, дубликаты, пригодность истории и доступность серверного запуска. Проверка не обучает модель.
- `POST /api/jobs` с `kind=forecast`: существующий контракт, права и лимиты. Завершённый результат новых задач содержит `data.report_snapshot` версии 1.
- `GET /api/jobs/{job_id}/report?lang=ru&format=html`: только владелец завершённой forecast-задачи. Форматы html/csv, языки ru/en. Чужая задача — 404, неверные параметры — 422, неподходящий статус или legacy-result без снимка — 409.
- Снимок содержит модель/версию, время построения, параметры, метрики, историю, все прогнозные значения и интервалы. Экспорт не читает исходный файл, не вызывает LLM, не переобучает модель и не расходует квоту. HTML округляет показанные значения до двух знаков; CSV сохраняет сохранённую точность.
- HTML не содержит скриптов или внешних ресурсов. CSV содержит фиксированные заголовки, ISO-даты и проверенные конечные числа; пользовательские названия не превращаются в формулы. Ответы имеют attachment, no-store, nosniff и ограничивающий CSP.

Новая таблица БД и миграция не нужны: снимок хранится в существующем результате постоянной задачи. Старые задачи не пересчитываются скрыто при скачивании. Для них нужен новый явно подтверждённый прогноз.

## Калибровка и редкие продажи

Исходный empirical-метод остаётся default. Экспериментальный split-метод разделяет выбор модели, калибровку и test, но не даёт заявленной гарантии для зависимых рядов. В preregistered synthetic-проверке он улучшил часть результатов и переоценил ширину диапазона для тренда. Поэтому он не включается в пользовательский маршрут по результатам одного эксперимента.

Ряды с большим числом нулей получают явную низкую надёжность. Полностью ненумерическая метрика отклоняется; неизвестные значения не превращаются молча в нулевые продажи. Согласованные реальные данные нужны для следующего этапа оценки.
