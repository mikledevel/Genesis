# Подготовка пилота — 14 ноября 2026

## Прогноз

В чате и прямом POST `/api/jobs` используется одна проверка реальных столбцов до enqueue. Имена целевого столбца из исходного сообщения учитываются, конфликт с аргументами LLM отклоняется, несколько дат требуют уточнения. Параметры горизонта переводятся в шаги до сохранения задания. Уточняющий ответ сохраняет исходную формулировку, включая горизонт. Сохранённые в PostgreSQL файлы восстанавливаются перед чтением.

## Реальные документы

Корпус Basecamp Handbook закреплён на commit `c9536061f26d0b5bd9f2f900d63e27e9f4deb4ed`. В Git входят вопросы и хеши файлов, а не копия чужого Handbook. Повторить:

```sh
git clone https://github.com/basecamp/handbook.git /tmp/genesis-handbook
git -C /tmp/genesis-handbook checkout c9536061f26d0b5bd9f2f900d63e27e9f4deb4ed
python eval/kb/real_corpus_eval.py --corpus /tmp/genesis-handbook --output artifacts/real-rag.json
```

Порог выбран только на dev: максимизировать корректные отказы при сохранении >=90% базовых top-3 попаданий. На heldout: default 0,16 — 29/34 найденных ответов, 12/16 отказов; выбранный для этого корпуса 0,18 — 28/34 и 14/16. Это улучшение отказов с потерей одного найденного ответа, а не гарантия корректности сгенерированного текста.

На дополнительных 8 вопросах к документации Genesis default даёт 4/8 попаданий, 4/4 отказов. Порог 0,18 снижает попадания до 3/8; поэтому staging сохраняет 0,16. Набор Genesis является диагностическим, не независимым heldout. Не следует переносить порог между базами знаний без проверки. `KB_RELEVANCE_GATE` задаёт конфигурацию; переданный явно `min_similarity` имеет приоритет.

Гибридный поиск с текущей мультиязычной MiniLM не улучшил эти реальные наборы при прежних параметрах: Basecamp heldout 29/34 и 12/16, Genesis 4/8 и 4/4. Дополнительный абсолютный dense-порог теряет слишком много ответов на dev. Hybrid остаётся опциональным, глобальные пороги не ужесточены.

## Staging и пилот

`render.staging.yaml` описывает отдельный Free web service, использующий уже созданную `genesis-ai-staging-db`. Production-сервис не входит в Blueprint. Startup создаёт частную схему только при явном `GENESIS_BOOTSTRAP_SCHEMA=true`, затем выполняет миграцию. В startup после миграции идемпотентно создаётся пилотная учётная запись Pro. Повторный hook не меняет существующий пароль. В режиме пилота публичная регистрация закрыта, платежи выключены.

Ветка `codex/pilot-readiness` готовится в отдельном чистом checkout подтверждённого репозитория. Локальный исходный каталог с untracked-файлами не превращается в общий baseline-коммит. Данные пользователя не копируются.

До успешного deploy, проверки рестарта и резервного восстановления staging не считается принятым. Фактическая обратная связь участника не подменяется автоматическими тестами. Сценарий и критерии: `docs/PILOT.md`.

## Проверка перед публикацией

На локальной одноразовой PostgreSQL проверены старт с пустой БД, миграция до версии 4, login, upload → очередь → обучение → сохранённая модель → прогноз, idempotency и отмена. После остановки сервера локальные каталоги моделей и загрузок убраны: сохранённые статусы и прогноз восстановились из БД. `pg_dump` восстановлен в другую одноразовую БД; аккаунт, задания и прогноз подтверждены. Это локальная проверка, не приёмка Render.

`POST /api/jobs` для train/forecast принимает `dataset_id` из результата upload, проверяет владельца и превращает ID в путь на сервере. Ошибки unsafe pickle и несовместимых признаков сохраняются при контейнерной проверке. Обычные тесты принудительно используют детерминированный dev runner; только тесты с маркером `real_docker` обращаются к реальному Docker.

```sh
GENESIS_TEST_POSTGRES_URL=postgresql://test_user@127.0.0.1:55441/test_db \
GENESIS_TEST_DOCKER=1 GENESIS_KB_CORPUS=/tmp/genesis-handbook \
python scripts/check_backend.py tests/ -q --tb=short
python scripts/staging_smoke.py --base-url https://STAGING_HOST \
  --credentials artifacts/pilot/credentials.json --checkpoint artifacts/pilot/staging-checkpoint.json
# После redeploy выполнить ту же команду с --verify-only.
```

Checkpoint содержит API-ключ, сохраняется с правами 0600 и не входит в Git. Автоматические smoke-операции нужно исключать из результатов человеческого пилота.

Итоговая локальная приёмка: 1123 passed, 1 skipped, 8 subtests passed (158,49 с); PostgreSQL, Docker и внешний корпус включены. Единственный skip — jsdom в изолированной Python-копии, UI проверен отдельно через Node. Live forecast routing: 3/3, медиана 602 мс, p95 717 мс, известная оценка стоимости $0,0014331. Эквивалентность 2 недель и 14 дней учитывается явно и проверена отдельным тестом.

## Развёрнутый staging

Сервис: https://genesis-ai-staging-2qpu.onrender.com. Отдельная PostgreSQL используется по частной сети. Основной HTTP smoke прошёл на Render: login, upload, built-in logistic training, idempotency, отмена, registry, predict.

Внешние подключения к БД закрыты. Для небольшого staging доступен `GET /api/pilot/backup`: только при `GENESIS_PILOT_ENABLED=true`, заданном `PILOT_EMAIL` и с токеном подтверждённого владельца. Ответ `application/gzip`, `Cache-Control: no-store`; все таблицы читаются в одном read-only repeatable-read transaction. Лимиты: 5000 строк на таблицу, 16 MB бинарных артефактов, 32 MB JSON. Этот ограниченный экспорт предназначен для пилота и не заменяет production PITR/pg_dump.

Серверный snapshot скачан и восстановлен в отдельную loopback-БД через `scripts/restore_pilot_snapshot.py`. В пустом каталоге подтверждены аккаунт, терминальные статусы задач, модель из бинарного артефакта и тот же прогноз. Restore-скрипт отклоняет внешний адрес БД и непустую цель. Файлы snapshot и credentials находятся только в `artifacts/pilot/` с правами 0600.

Дополнительная проверка настоящего Groq на Render: 4/4 — уточнение income, прогноз с версией/метриками/ограничениями, ответ по загруженному документу с валидным источником, отказ назвать неизвестный сертификат. Это автоматическая техническая приёмка, не человеческий пилот. Дополнительные тесты startup, доступа к backup и PostgreSQL snapshot: 28 passed.
