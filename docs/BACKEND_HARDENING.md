## Контракты

Для платных `POST /api/marketplace/{listing_id}/use`, `/api/models/{model_id}/predict` и `/api/v1/chat/completions` поддерживается `Idempotency-Key`. Для сообщений агента передаётся `request_id` в JSON. Повтор использует тот же ключ и тот же payload; повтор ключа с иными параметрами возвращает 409. Идентификаторы генерирует клиент до отправки. Финансовые резервы, оставшиеся после аварии, обрабатывает maintenance worker; неопределённый расход токенов учитывается по резерву.

Создание задания: `POST /api/jobs` с `{"kind":"model_build","payload":{...}}`; также доступны `retrain` и `improve`. Payload соответствует существующим ML-контрактам. Ответ 202 содержит `job_id` и `status_url`. `GET /api/jobs/{id}` возвращает состояние и прогресс, `DELETE` запрашивает отмену. Задания выполняются в дочерних процессах с ограничениями времени и ресурсов.

Ошибки сохраняют `detail`; обработчики добавляют `code` и `request_id`. Список ключей показывает только маску, полный ключ выдаётся при создании. Отзыв выполняется по ID. Ключи в БД хешируются, digest не принимается как bearer.

## Запуск и миграция

Перед обновлением сохраните резервную копию, стабильный `SECRET_KEY` и `INTEGRATION_ENCRYPTION_KEY`. Последний можно оставить пустым: тогда ключ шифрования выводится из `SECRET_KEY`; его замена требует отдельной миграции зашифрованных значений.

```sh
python scripts/backup_db.py
DATABASE_AUTO_MIGRATE=true python scripts/migrate.py
python scripts/migrate.py --check
```

Затем запускайте приложение с `DATABASE_AUTO_MIGRATE=false`. Render startup выполняет этот порядок автоматически. Мигратор импортирует конфигурации legacy JSON, хеширует прежние API-ключи и шифрует Telegram-токены. Сами файлы старой SQLite-инсталляции нужно сохранить и переносить вместе с БД.

`TRUSTED_PROXY_CIDRS` содержит только фактические адреса reverse proxy; не добавляйте туда весь интернет. Uvicorn запускается с `--no-proxy-headers`. Для production внешних моделей нужен доступный Docker runner и образ `genesis-sandbox:latest`.

## Данные и восстановление

При `DATABASE_URL` резервная копия создаётся `pg_dump --format=custom --schema=genesis`. Нужны клиентские PostgreSQL tools совместимой версии. Храните dump отдельно от сервера. Восстановление выполняйте в новую БД с подготовленной приватной схемой и ролями через `pg_restore --no-owner --no-acl`; сначала проверьте `/ready`, аккаунты, ledger, диалоги и восстановление файлов, затем переключайте приложение.

Поддерживаемые файлы PostgreSQL: до 64 MiB на файл и 500 MiB на аккаунт, относительные storage keys и SHA-256. Новые файлы сохраняются автоматически; существующие локальные файлы не считаются перенесёнными только от установки `DATABASE_URL`.

При SQLite `backup_db.py` сохраняет согласованную копию БД через SQLite backup API. Каталоги `datasets`, `models`, `registry`, `generated`, `agents`, `blocks`, `marketplace` резервируйте отдельно при остановленных файловых операциях. SQLite backup не является архивом всех этих каталогов.

## Границы выполненного пакета

Совместимые старые синхронные ML-маршруты сохранены; для длительных задач используйте `/api/jobs`. Локальная development-изоляция слабее Docker и допускается только в debug. Доставка внешних событий имеет семантику at least once: если внешний сервис принял запрос, а процесс завершился до подтверждения, возможен повтор. Получателям webhook следует дедуплицировать события.

Общий frontend остаётся преимущественно одним файлом; полный перенос на модули, полное разделение legacy GenesisDB на репозитории, dashboard метрик/p95 и нагрузочное профилирование — отдельные работы. HTTP-журнал и ограничение выборок не заменяют такую эксплуатационную систему. Эти архитектурные направления исходного аудита не объявляются полностью завершёнными.

## Результаты проверки

- Python 3.12, изолированная копия приложения и одноразовый PostgreSQL 18: **1053 passed, 6 skipped**, 8 subtests, 158 секунд. Docker-тесты запускаются отдельно; тесты стороннего корпуса и jsdom внутри очищенной Python-копии требуют дополнительных ресурсов. Пропуски не учитываются как успешные проверки.
- Отдельный прогон реального Docker: **3 passed** — отсутствие сети, непривилегированный UID, read-only rootfs, внешняя модель и проверка качества, файловый мост навыка с замоканным внешним HTTP.
- Финальный набор regressions и PostgreSQL: **37 passed**, включая настоящий dump/restore в другую одноразовую БД, аккаунты, диалоги и файловые артефакты.
- Все три jsdom-набора (`ui_test`, `admin_test`, `antibot_test`) завершились успешно; `pip check` и компиляция Python-модулей прошли.
- Playwright на отдельном локальном сервере: вход тестового пользователя, открытие настроек, маска ключа, запрет повторного копирования и отзыв ключа. Ошибок консоли нет. Платные LLM-вызовы не выполнялись.
- Независимое read-only ревью выявило три оставшихся edge case: конфигурация бота между расчётом оплаты и генерацией, replay при потраченном балансе и истечение последней аренды outbox. Все три исправлены и покрыты регрессиями.

Это локальная проверка, а не результат запуска CI на GitHub или проверки production-среды. Известные уязвимости зависимостей отдельным advisory scanner в этом прогоне не проверялись.
