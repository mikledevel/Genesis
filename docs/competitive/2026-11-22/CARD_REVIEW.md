# Проверка разовых отчётов и Stripe

Проверено 23 ноября 2026. Исследовалась версия `app/core/report_quotes.py` с `checkout_deadline=now+1800`, постоянным ключом `report-refund-{quote_id}` и ранним выходом из `apply_refund` при `status=refunded`. Номера строк ниже относятся к этому состоянию до исправлений основным агентом.

Прочитаны `app/routers/report_quotes.py`, webhook в `app/routers/auth.py`, dispatch в `app/core/payments.py`, транзакции `DatabaseDocument` и существующие тесты. Использованы Stripe best-practices/payments/security и публичная официальная документация. Для новой интеграции код задаёт `StripeClient`, API `2026-11-18.endive`; SDK ожидается 17.1.0. Фактическая совместимость в Stripe sandbox не проверялась. Connector недоступен; Stripe CLI в PATH отсутствует. Ни один платёжный API не вызывался.

## Подтверждённые проблемы

### 1. P1: успешный возврат может потеряться между получением Session и записью paid

**Место:** `app/core/report_quotes.py:205–207`, `:209–213`, `:129–134`; `app/routers/auth.py:243–257` возвращает 200 для результата обработчика.

Сценарий:

1. Обработчик `checkout.session.completed` получает Session: оплата paid, `latest_charge.refunded=False`, но ещё не вызывает `mark_paid`.
2. Возврат проходит, и его `charge.refunded` обрабатывается раньше записи paid. В quote ещё нет `payment_intent`. Обработчик возвращает `refund_not_confirmed`, webhook подтверждается ответом 200.
3. Первый обработчик продолжает работу со старым снимком Session и записывает `paid`. Заказ может быть выдан после полного возврата. Следующее событие, исправляющее состояние, не гарантировано.

**Локальное воспроизведение:** новая временная SQLite, фиктивный аккаунт, StripeClient заменён Mock. Callback на `sessions.retrieve` сначала обрабатывает refund-событие, затем возвращает ранее полученный paid-снимок. Получено:

```text
Refund between retrieve and mark_paid: refund_not_confirmed
Paid webhook after successful refund: paid
Final local status after refunded charge: paid
```

Существующий тест `test_refund_before_payment_webhook_does_not_resurrect_paid_order` проверяет другой порядок: Session уже отражает возврат к моменту получения. Он не закрывает описанную гонку. Stripe прямо не гарантирует порядок доставки и предлагает получать недостающие объекты при необходимости. [Webhook ordering](https://docs.stripe.com/webhooks#event-ordering).

**Узкое исправление:** refund-событие для ещё не привязанного PaymentIntent должно надёжно откладываться/повторяться, а не подтверждаться как окончательно обработанное. Сохранить проверенную привязку и незавершённое событие транзакционно, затем сверить текущий платёж/возвраты. Минимальный вариант — возвращать retryable ошибку для корректного, но пока неприменимого события и обеспечить последующую сверку. Проверить именно interleaving между retrieve и `mark_paid`.

### 2. P1: expires_at находится на нижней границе Stripe ещё до обращения к API

**Место:** `app/core/report_quotes.py:83–100`.

Приложение сохраняет `checkout_deadline=now+1800` до завершения локальной транзакции и сетевого запроса. Stripe требует срок не меньше 30 минут от текущего времени/создания Session. Даже задержка в две секунды даёт Stripe оставшийся срок 1798 секунд, который нарушает контракт. Если первоначальное создание не состоялось, последующий повтор сохраняет уже укороченный срок. [Session create, expires_at](https://docs.stripe.com/api/checkout/sessions/create), [Timed expiration](https://docs.stripe.com/payments/checkout/managing-limited-inventory.md?ui=full-page).

**Локальная проверка:** часы приложения зафиксированы, mock API проверяет опубликованное ограничение с задержкой две секунды. Параметр имеет 1798 секунд до истечения, проверка отклоняет запрос. Это проверка запроса по контракту, не реальный ответ Stripe.

**Узкое исправление:** задать запас, например час, либо использовать default 24 часа; согласовать срок с политикой quote. Сохранять параметры одной попытки неизменными. Для сохранённой Session использовать её ID, не создавать заново на каждый запрос. Отдельно обработать восстановление неизвестного результата создания/истёкшей попытки: нельзя просто менять `expires_at` под прежним idempotency key.

### 3. P2: неудавшийся возврат нельзя повторить как новую попытку

**Место:** `app/core/report_quotes.py:181–190`, постоянный ключ `report-refund-` + quote ID.

После `failed/canceled` локальный заказ возвращается в paid/ready и API снова разрешает `refund`. Но новый вызов идёт с тем же ключом. Stripe API v1 сохраняет первый результат и возвращает его при повторе ключа. Поэтому повторная административная команда получает старый Refund, вместо создания новой попытки. Если первоначальный ответ был pending, а Refund затем failed, повтор может также вернуть старое pending-представление и снова закрыть выдачу без нового возврата. [Stripe idempotency](https://docs.stripe.com/api/idempotent_requests).

**Узкое исправление:** хранить `refund_attempt_id` и `refund_id`. Повторы одной неопределённой сетевой операции используют прежний ключ. Состояние существующего Refund получать через retrieve. После подтверждённого failed/canceled новая осмысленная попытка получает новый UUID/ключ под транзакционной блокировкой. Успешный либо ещё выполняющийся возврат не запускается повторно.

### 4. P2: refunded ошибочно считается безусловно окончательным состоянием

**Место:** `app/core/report_quotes.py:161–162`, `:173–174`.

`apply_refund` возвращает `already_processed` при любом `q.status=refunded`, не проверив актуальный `refund.status`. Stripe описывает поздний отказ банка и для ряда способов оплаты переход `succeeded → requires_action → failed/canceled`. В таких случаях средства возвращаются на Stripe balance, но локальный заказ остаётся refunded, отчёт недоступен, а организатор не получает состояние требуемого повторного расчёта. [Failed refunds и requires_action](https://docs.stripe.com/refunds#failed-refunds).

**Локальное воспроизведение:** `apply_refund` для одного Refund со статусом succeeded, затем failed даёт `refunded`, `already_processed`; итог остаётся refunded.

**Узкое исправление:** сверять актуальный Refund ID и его состояние, хранить статус возврата отдельно от оплаты/выдачи. Failed/requires_action после succeeded должны переводить заказ в явное состояние незавершённого возврата/ручной сверки, а не безусловно игнорироваться. Нужна бизнес-политика доступа и повторной выплаты; автоматически обещать клиенту завершённый возврат в таком состоянии нельзя.

## Что не признано проблемой

- Цена и валюта задаются административным API и читаются сервером из quote. Клиентский Checkout-body пустой, лишние поля запрещены.
- Выдача и возврат закрыты `require_admin`. Для выдачи выбирается завершённое forecast-задание текущего администратора; клиент скачивает только quote своего namespace.
- Webhook проверяет подпись; return/success URL не выдаёт отчёт сам по себе. Обрабатываются completed и async_payment_succeeded, платёжный статус, amount/currency, user/quote/attempt и Session ID.
- Session metadata явно дублируется в `payment_intent_data.metadata`. Stripe переносит metadata PaymentIntent в Charge однократным снимком; это соответствует `charge.refunded`. Метаданные произвольных связанных объектов сами по себе не наследуются. [Metadata](https://docs.stripe.com/metadata).
- Транзакции документа защищают локальные переходы от повторной выдачи и повторного `mark_paid`. Они не закрывают гонку с внешним снимком Stripe, описанную в пункте 1.
- Приоритетный dispatch report-событий предотвращает зачисление стоимости отчёта в wallet и выдачу подписки. Ошибок обхода owner/admin boundaries в проверенных маршрутах не подтверждено.

## Границы результата

Временные проверки не использовали `.env`, реальную БД, реальные ключи или данные покупателей. Код приложения и тесты не изменялись. Четыре пункта относятся к проверенной версии до правок. После исправлений нужны регрессии указанных последовательностей и разрешённый отдельный sandbox-прогон; наличие административного API возврата не является разрешением совершать реальный возврат.


## Исправления после проверки

Все четыре замечания исправлены в текущем исходном коде. Непривязанное событие возврата получает повторяемую ошибку 503, а не подтверждение обработки. Срок Checkout увеличен до часа с неизменными параметрами повторов. У возврата есть сохранённый UUID попытки; после отказа создаётся новый, устаревшие Refund ID не меняют новую попытку. Поздние requires_action/failed восстанавливают корректное состояние. Уведомления возврата без своей metadata связываются через PaymentIntent.

Регрессионные тесты воспроизводят возврат между чтением Checkout и записью оплаты, успешный→requires_action→failed, новую попытку после отказа, игнорирование старого события, подпись webhook, конкурентные дубли и выдачу отчёта Free-пользователю. Это локальная проверка с имитацией платёжного провайдера, а не результат настоящей оплаты или Stripe sandbox.
